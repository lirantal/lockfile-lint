# Bundled integrity fixtures

These lockfiles were generated by npm 10.9.2 (Node 22.14.0) by packing and
installing a local package, rather than assembling the bundle metadata by hand.
The tarball itself is not needed by tests: validation reads lockfile metadata
without fetching packages. The tests clone and mutate these fixtures to exercise
invalid bundle ancestry.

To regenerate, create sibling directories `bundler`, `v2` and `v3`. Put this
`package.json` in `bundler`:

```json
{
  "name": "bund2",
  "version": "1.0.0",
  "private": true,
  "bundleDependencies": ["debug"],
  "dependencies": {"debug": "4.3.4"}
}
```

Run in `bundler`:

```sh
npm install --ignore-scripts --no-audit --no-fund
npm pack --ignore-scripts
```

In each of `v2` and `v3`, create this `package.json`:

```json
{"name":"bundle-fixture","version":"1.0.0","private":true}
```

Run the matching command in each directory and copy the resulting lockfile:

```sh
# v2
npm install ../bundler/bund2-1.0.0.tgz debug@4.3.4 ms@2.0.0 --lockfile-version=2 --ignore-scripts --no-audit --no-fund
# v3
npm install ../bundler/bund2-1.0.0.tgz debug@4.3.4 ms@2.0.0 --lockfile-version=3 --ignore-scripts --no-audit --no-fund
```

`bund2` bundles `debug` and its transitive dependency `ms@2.1.2`. The separately
installed `debug` also has a nested, unbundled `ms@2.1.2`, because the consumer
pins top-level `ms@2.0.0`. That entry reproduces the forged `inBundle` attack.
The v1 tests use the npm-generated legacy `dependencies` tree from the v2
fixture; it has `bundled` flags and no parent `bundleDependencies` declaration.
